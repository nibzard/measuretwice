Check an AI message before your app uses it.

measuretwice is a proposed TypeScript library for checking AI judgments against requirements you define.

Write the requirements in readable YAML. Your app gets a report showing which checks pass, fail, or need review.

This guide demonstrates the proposed design. The examples are simulated; no model calls run here.

01

Should this assistant send this message?

Cassandra is an assistant that notices conflicts in team discussions. It has drafted a warning about moving customer data.

The earlier decision

Customer export data must remain in the EU.

The team discussion

Let us move the export worker and its data to the US region. A teammate replies: that conflicts with our EU requirement; we must keep the data in the EU.

The assistant’s draft

This move conflicts with our EU data location requirement. Keep the export data in the EU.

Example report

The message repeats a concern.

Is there a real conflict?Pass
Is the message supported?Pass
Does it add new information?Fail

A participant has already acknowledged this concern.

Does it need an interruption?Pass
Execution complete · all checks assessedFail

Inspect the failed check before using this message.

In “Already discussed,” the warning is accurate, but it repeats a concern the team has raised. The novelty check catches that.

These explanations are authored for the demonstration. Checks can only assess the supplied context.

What do the results mean?
ResultMeaning
PassThe assessment meets this check under the selected decision rules.
FailThe assessment meets an unacceptable outcome under those rules.
ReviewThe evidence or assessment does not support an automatic decision.
ErrorExecution or validation failed.
SkippedThe check was not attempted. The report records the reason.

All four checks are required. Any fail makes the overall result fail. Otherwise, error takes priority, followed by review or skipped, then pass.

The report preserves every result. A failure does not hide an execution error in another check.

02

Write what you want to check.

Start with one requirement: the assistant’s claims must follow from the evidence. This YAML tells measuretwice what that means.

- id: message-supported
  name: Our message accurately describes the evidence
  using: [prior_decision, conversation, proposed_message]
  question: Does every material claim in the proposed message follow from the evidence?
  answers:
    supported: All claims are supported with appropriate certainty and attribution.
    contradicted: A material claim conflicts with the supplied evidence.
    incomplete: Support for a material claim is missing or ambiguous.
  accept: supported
  review: incomplete
using

The inputs this check can read.

question + answers

What to assess, and what each possible answer means.

accept: supported

The answer that meets your requirement.

review: incomplete

An answer that needs review. “Contradicted” is unacceptable.

The other checks describe conflict, novelty, and consequence in the same file. You can read the requirements without learning the model’s API.

Read the complete four-check YAML
version: 1
name: intervention-review
when_uncertain: review

inputs:
  prior_decision: { type: string, minLength: 1 }
  conversation: { type: string, minLength: 1 }
  proposed_message: { type: string, minLength: 1 }

checks:
  - id: decision-conflict
    name: An earlier decision is being contradicted
    using: [prior_decision, conversation]
    question: How does the new proposal relate to the earlier decision?
    answers:
      conflict: It conflicts with a decision that still applies.
      replaced: The team explicitly replaced the earlier decision.
      aligned: It is compatible with the earlier decision.
      unclear: Applicability or the relationship cannot be established.
    accept: conflict
    review: unclear

  - id: message-supported
    name: Our message accurately describes the evidence
    using: [prior_decision, conversation, proposed_message]
    question: Does every material claim in the proposed message follow from the evidence?
    answers:
      supported: All claims are supported with appropriate certainty and attribution.
      contradicted: A material claim conflicts with the supplied evidence.
      incomplete: Support for a material claim is missing or ambiguous.
    accept: supported
    review: incomplete

  - id: adds-information
    name: We are adding something new
    using: [conversation, proposed_message]
    question: Has the conversation already acknowledged this concern?
    answers:
      "yes": A participant explicitly recognizes this specific concern.
      "no": No supplied message explicitly recognizes this specific concern.
    accept: "no"

  - id: consequence
    name: The concern warrants an interruption
    using: [prior_decision, conversation, proposed_message]
    question: What consequence does this concern have, based on the evidence?
    scale:
      - minor: A wording or preference difference with no identified operational consequence.
      - meaningful: A coordination problem causing rework or delay.
      - serious: A conflict affecting an explicit customer commitment or operational requirement.
    accept:
      at_least: meaningful
Use a simple rule for an exact requirement

A message length limit runs in code. It does not need a model judgment.

id: message-length
name: The message fits our delivery limit
using: [proposed_message]
rule:
  maxLength: 900
03

Try it without changing your app’s decisions.

Start with a shadow run: measuretwice records its result while your existing application policy stays in control.

Proposed TypeScript API
import { load } from "measuretwice";

const reviewer = await load(
  ".measuretwice/checks/intervention.yaml",
  { profile: ".measuretwice/profiles/intervention.json" },
);

const report = await reviewer.run({
  id: proposal.id,
  input: {
    prior_decision: priorDecisionWithSources,
    conversation: recentConversation,
    proposed_message: proposal.text,
  },
}, {
  mode: "shadow",
  baseline: { outcome: existingDecision, revision: "policy-1" },
});

await saveReport(report); // Application-owned storage.

Load the requirements and settings

The YAML contains your checks. A profile records the model and code versions, decision rules, and evaluation evidence.

Supply the case

A case is the input you want to assess. Here, it includes the decision, conversation, and proposed message.

Read the report

Compare the result with your existing decision. Your application controls storage, permissions, and message delivery.

The starter profile is explicitly unvalidated. Use it for exploration and shadow runs.

Awaiting a shadow run still takes time and provider usage. Your application can use its own queue for background work.

04

Use reviewed examples to improve the decisions.

Before your app relies on these results, test them against cases with reviewed judgments. Your coding agent can help prepare the work.

You and your agent prepare examples

The agent drafts cases, including ambiguous ones. Reviewers label them. Keep AI suggestions separate from human judgments.

You set the goals; code tests the decision rules

Decide which errors matter and how much review you can accept. Code finds settings using one set of examples. It tests those fixed settings on a separate set.

You inspect the evidence and select a profile

The report shows errors, review burden, and uncertainty. If evidence is insufficient, gather more cases. The agent does not approve a profile automatically.

This process is calibration. It produces inspectable settings for interpreting model output. Numerical details stay in the profile, separate from your readable requirements.

When you change a check or model, evaluate the change again. Earlier results do not qualify the new version.

Before using a profile to guide live decisions, confirm that it matches the checks and evaluator. It must meet your goals for the intended use.

Details when you need them

Use these sections to inspect the implementation, numerical policy, or proposed API.

What does the model actually do?

An evaluator is the component that assesses a check. The first semantic evaluator uses Jev through the TypeSafe SDK.

The adapter translates your question and answer descriptions into the provider’s request format.

Your checkJev primitive
Named answers, such as supported or contradictedChoice
Exactly yes and noNoul
An ordered scale, such as minor, meaningful, seriousScore

The evaluator returns an assessment: the provider’s actual measurement. The profile’s decision rules turn that assessment into pass, fail, or review.

The report retains both the measurement and the applied rule. Exact checks, such as a length limit, run in code.

The MVP includes Jev and exact rules. Other model and tool adapters are future work.

What happens during a run?

Each check receives only the inputs named in using. Questions can share a call only when their authorized input state is identical.

Bound the work

Limit concurrency, queue size, retries, and total time. The deadline includes queue and retry time.

Preserve failures

A timeout is an error. Saturated work can be skipped. Neither becomes a pass.

Control storage

The library does not store raw input by default. The host saves reports and source snapshots.

How does calibration work?

An agent can guide calibration. Tested statistical code calculates results. The owner sets goals and reviews the evidence.

Four possible qualification results

unvalidatedNo completed qualification.
insufficient_evidenceToo little reliable evidence.
criteria_not_metThe evidence does not meet the goals.
validated_for_scopeThe evidence meets the declared goals for the evaluated scope.

Define the error denominator

Error among accepted cases
Incorrectly accepted ÷ all accepted cases.

False acceptance rate
Incorrectly accepted ÷ all unacceptable cases.

These answer different questions. The calibration plan must name the intended metric.

Explore a numerical policy · synthetic demonstration

This binary example accepts “no.” Move the values to see how an explicit policy can return pass, fail, or review.

Green: acceptable mass. Remaining area: unacceptable mass.

Applied policy

Pass if acceptable mass ≥ selected cutoff.
Fail if unacceptable mass ≥ 80%.
Otherwise review.

Review

These controls demonstrate the decision arithmetic. The starter values are arbitrary and have no supporting calibration evidence. Provider mass does not establish a probability of correctness.

For Score, sum mass over acceptable named levels. Do not round the mean. A Choice answer explicitly marked for review remains review. Optional Choice/Score confidence floors can add review. Noul has no separate confidence field.

Synthetic challenge cases help find failures. They do not establish production error rates. Zero observed errors does not prove zero risk.
What happens when I change the model?

The requirement can stay the same when the evaluator changes. The old qualification cannot transfer to the new evaluator.

Demonstration: the host could select this compatible, qualified profile. The report alone cannot authorize an action.

A new question, translation, schema, input projection, or preprocessing step can also invalidate qualification. Population changes require new evidence, even without a changed hash.

How future LLM and tool adapters fit

The adapter returns a typed assessment or an execution error. It preserves supported measurements and does not invent confidence values.

A label-only backend needs its own evaluated decision rule. Function calling specifies output structure; it does not establish correctness.

The host registers evaluators and tool permissions. YAML cannot install an adapter, execute arbitrary code, or grant tool access.

What is included in the MVP?

Start with Jev and exact rules. Test the workflow with Cassandra and compare it with direct SDK use.

Already available in this repository

The development check definitions cover example consistency and claim evidence. They include 18 synthetic cases.

The labels are agent-proposed and human-unreviewed. No runner or model-quality result is established by these files.

Outside v0

  • Other production semantic backends
  • A hosted dashboard or authoring service
  • Autonomous profile promotion
  • A formal-verification evaluator
  • Claims of calibrated correctness probabilities
The pilot should test whether developers can read, evaluate, and maintain AI decisions more easily than with a direct type-safe SDK.
Can I write checks in TypeScript?

defineChecks builds the same serializable definition. Equivalent YAML and TypeScript produce the same canonical definition and hash.

import { defineChecks } from "measuretwice";

const checks = defineChecks({
  version: 1,
  name: "novelty-review",
  when_uncertain: "review",
  inputs: {
    conversation: { type: "string" },
    proposed_message: { type: "string" },
  },
  checks: [{
    id: "adds-information",
    name: "We are adding something new",
    using: ["conversation", "proposed_message"],
    question: "Has the conversation already acknowledged this concern?",
    answers: {
      yes: "A participant explicitly recognizes this specific concern.",
      no: "No supplied message explicitly recognizes this specific concern.",
    },
    accept: "no",
  }],
});

Applications import trusted TypeScript. The CLI does not execute arbitrary TypeScript definitions.

Where do the files live?

The project folder

The following files illustrate the convention. The Cassandra artifacts are proposed.

.measuretwice/checks/intervention.yaml

Requirements that people review.

.measuretwice/cases/intervention.jsonl

Input cases, labels, and label provenance.

.measuretwice/calibration-plan.json

Goals, sampling, splits, and permitted numerical policies.

.measuretwice/profiles/intervention.json

Exact evaluator binding, decision rules, and evaluation evidence.

.measuretwice/reports/

Generated reports. Ignored by default; retain qualification evidence in managed storage.

Proposed CLI workflow
measuretwice validate .measuretwice/checks/intervention.yaml

measuretwice calibrate .measuretwice/checks/intervention.yaml \
  --plan .measuretwice/calibration-plan.json \
  --out .measuretwice/profiles/candidate.json

measuretwice run .measuretwice/checks/intervention.yaml \
  --profile .measuretwice/profiles/candidate.json \
  --case example.json --mode shadow

measuretwice inspect .measuretwice/profiles/candidate.json

The MVP also proposes evaluate and compare. These commands are not implemented in this repository yet.
